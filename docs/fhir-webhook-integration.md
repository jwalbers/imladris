# Imladris Radiology Integration — FHIR R5 + Webhook Architecture

**Audience:** OpenMRS developers and integration engineers.
**Purpose:** Explain how OpenMRS radiology orders flow to AdvaPACS and back,
using FHIR R5 ServiceRequests and AdvaPACS webhooks as the integration backbone.

---

## Overview

The integration connects three systems:

```
OpenMRS (EMR)  ←──HL7──→  Imladris Sidecar  ←──FHIR/Webhook──→  AdvaPACS (PACS/RIS)
                                   │
                           DICOM C-STORE / MWL
                                   │
                              Modality (X-ray, US…)
```

The **sidecar** is a Python service that acts as a translation layer. It speaks
HL7 v2 to OpenMRS and FHIR R5 + DICOM to AdvaPACS. OpenMRS never talks directly
to AdvaPACS.

---

## Outbound path: OpenMRS → AdvaPACS

### 1. Order placed in OpenMRS

A clinician places a radiology order in OpenMRS (Radiology App module). This
generates an HL7 **ORM^O01** message containing:

- Patient demographics (name, ID, DOB, sex)
- Procedure code and description
- Accession number
- Study Instance UID (generated by OpenMRS Radiology App, used to link
  the eventual DICOM study back to the order)

### 2. Sidecar translates ORM → FHIR ServiceRequest

The sidecar's `order_poller` receives the ORM^O01 and POSTs a **FHIR R5
ServiceRequest** to the AdvaPACS integration API:

```
POST https://usa1.api.integration.advapacs.com/fhir/R5/ServiceRequest
Authorization: ID={key_id},Secret={key_secret}
Content-Type: application/fhir+json
```

Key fields mapped from ORM to ServiceRequest:

| ORM field | FHIR ServiceRequest field |
|-----------|--------------------------|
| Patient ID | `subject` → Patient resource (found or created by identifier) |
| Procedure description | `code.concept.coding[].display` |
| Accession number | `identifier[]` with type code `ACSN` |
| Study Instance UID | `identifier[]` with system `urn:dicom:uid` |
| Modality | `orderDetail[].parameter[].valueString` (code = `modality`) |

The ServiceRequest is created with **`status: draft`** — meaning it is pending
radiologist review in AdvaPACS. No imaging can start yet.

### 3. DICOM Modality Worklist

Once the ServiceRequest exists in AdvaPACS, two paths deliver it to the imaging
room:

**Path A — Native DICOM MWL (physical modalities):**
The AdvaPACS gateway (port 11112) natively implements a DICOM Modality Worklist
SCP (SOP class `1.2.840.10008.5.1.4.31`, confirmed in the
[AdvaPACS DICOM Conformance Statement](https://conformance.advapacs.com/overview/dimse-services)).
A real CR/DR/US room queries it directly with a C-FIND. No sidecar involvement.

**Path B — Synthesized MWL (modality console / simulator):**
The sidecar's `fhir_mwl_poller` polls AdvaPACS FHIR every 30 seconds for
`status=draft,active` ServiceRequests and writes one `.wl` file per order. The
modality console (a web UI) reads these files to display the worklist.

## Order status lifecycle

AdvaPACS maps its internal order states to FHIR `ServiceRequest.status`:

| AdvaPACS UI label | FHIR status | Modality console badge |
|-------------------|-------------|------------------------|
| Draft | `draft` | **Pending Review** (blue) |
| In Progress | `active` | **Approved** (green) |
| Complete | `completed` | **Completed** (grey) |
| — | `revoked` | **Cancelled** (red) |

The radiologist/order approver changes the state in the AdvaPACS UI. The sidecar
learns about each change via webhook (see below). Imaging is only permitted when
`status=active`.

## Inbound path: AdvaPACS → OpenMRS

### 4. AdvaPACS fires webhooks

When a ServiceRequest is created or its status changes, AdvaPACS POSTs a webhook
to the sidecar's `/events` endpoint:

**ORDER_CREATED** (fires immediately on creation):
```json
{
  "event": "ORDER_CREATED",
  "data": { "id": "fhir-uuid-of-the-servicerequest" }
}
```

**ORDER_UPDATED** (fires on every status change):
```json
{
  "event": "ORDER_UPDATED",
  "data": { "id": "fhir-uuid-of-the-servicerequest" }
}
```

> **Important:** The webhook payload contains only the FHIR resource UUID — not
> the accession number, not the new status. The sidecar must immediately fetch
> the full ServiceRequest (and linked Patient) from the FHIR API to get the
> current state and patient demographics.

### 5. Sidecar fetches ServiceRequest + Patient

```
GET /fhir/R5/ServiceRequest/{uuid}   → status, accession, study UID, procedure
GET /fhir/R5/Patient/{uuid}          → name, DOB, sex
```

This fetch happens in a background thread within ~2 seconds of the webhook. The
sidecar updates its in-memory `_order_states` dict and persists to
`/data/order_states.json`. The modality console reflects the new status on next
page refresh (no polling needed — the webhook already updated the state).

### 6. ORU^R01 sent to OpenMRS on completion

When `status=completed` is detected:

```
sidecar → OpenMRS HL7 listener
          ORU^R01 message
          OBR: order/accession details
          OBX: "STUDY COMPLETE" observation
```

This signals OpenMRS that the imaging study has been accepted by the radiologist.
A second ORU^R01 carrying the structured report text is on the integration
roadmap (triggered by AdvaPACS `REPORT_CREATED` webhook).

## Data flow diagram (full cycle)

```
Clinician (OpenMRS)
  │  places radiology order
  ▼
OpenMRS Radiology App
  │  ORM^O01
  ▼
Sidecar order_poller
  │  POST ServiceRequest {status:draft}
  ▼
AdvaPACS FHIR R5 API ──────────────────────────────────┐
  │  ORDER_CREATED webhook                              │
  ▼                                                     │
Sidecar /events                                         │
  │  GET ServiceRequest + Patient                       │
  ▼                                                     │ DICOM
_order_states {status:draft}                            │ C-FIND
  │  fhir_mwl_poller writes .wl                         │ (MWL)
  ▼                                                     │
Modality console: "Pending Review" (Image Patient grey) │
                                                        │
Radiologist approves in AdvaPACS                        │
  │  ORDER_UPDATED webhook {status:active}              │
  ▼                                                     │
Sidecar updates _order_states                           │
  ▼                                                     │
Modality console: "Approved" (Image Patient green)      │
                                                        ▼
Rad tech clicks Image Patient ──────────────────── Modality
  │  DICOM C-STORE (with accession + study UID)
  ▼
AdvaPACS Gateway → AdvaPACS Cloud
  (Qure.ai AI analysis attached as Secondary Capture)

Radiologist reviews images + AI overlay, marks Complete
  │  ORDER_UPDATED webhook {status:completed}
  ▼
Sidecar → ORU^R01
  ▼
OpenMRS: order fulfilled
```

## Key identifiers and join keys

| Identifier | Where it lives | Purpose |
|------------|---------------|---------|
| **Accession number** | ORM MSH/OBR, FHIR `identifier[ACSN]`, DICOM `AccessionNumber` | Links ORM → ServiceRequest → DICOM study |
| **Study Instance UID** | ORM ZDS segment, FHIR `identifier[urn:dicom:uid]`, DICOM header | Links ServiceRequest → DICOM images in AdvaPACS |
| **FHIR ServiceRequest UUID** | AdvaPACS webhook `data.id`, FHIR resource `id` | Used by sidecar to fetch current state from FHIR after webhook |
| **AdvaPACS Patient UUID** | FHIR `Patient.id`, `ServiceRequest.subject.reference` | Links demographics across FHIR resources |

---

## What OpenMRS does not need to change

- OpenMRS sends standard HL7 ORM^O01 and receives standard HL7 ORU^R01.
- The sidecar handles all FHIR translation — OpenMRS is unaware of FHIR.
- The Study Instance UID generated by the OpenMRS Radiology App is the only
  non-standard requirement: it must be included in the ORM (ZDS segment) so the
  sidecar can pass it through to the FHIR ServiceRequest and then into the DICOM
  worklist, ensuring the modality tags its images with the correct UID.
